# 设计：受管区从「固定三角色」改为「运行时能力 + 分工规则」

## 原则

受管区是**写一次、长期存在**的文本，它只能承载稳定的事实与规则；易变的事实（本会话注册了哪些 kind）必须指向运行时读取点 `/Coworkflow:status`，或写成带条件的表述。

因此分两类内容：

| 内容 | 稳定性 | 写法 |
|---|---|---|
| kind ↔ Trellis 角色（implement / check / research） | 稳定（由 kind 表的 role 决定） | 写死对应关系 |
| 本会话可派哪些 agent、上限、是否启用 | 易变（会话、面板、注册） | 指向 `/Coworkflow:status`，禁止列举 |
| 分工、不可用时的行为、与 Trellis inline 的优先级 | 稳定 | 写清规则 |

## 要改的三处

### 1. 能力段

现状：一张写着「执行者 `cw-executor` / 审计者 `cw-auditor` / 调研者 `cw-researcher`」的表，并断言「类型就是这三个」。

改为：

- 说明「本项目可派的 kind 与其 agent 名以 `/Coworkflow:status` 输出的 `agent-kinds` 行为准」；
- 保留「kind 与 Trellis 角色一一对应、`cw-*` 额外经过项目开关与上限」这条**稳定**语义；
- 明确 `trellis-*` 不是推荐目标的原因（绕开开关与上限），但把「不要用」改成「不可用时的替代不是 `trellis-*`」。

### 2. 不可用时的行为（新增）

新增一小节，三条：

1. 派单失败或 status 里没有该 kind → 读出原因（未启用 / 未注册 / 契约不可用 / 上游拒绝）。
2. 处理的顺序：改派到**已列出的** kind → 把该工作单元收回主会话自己做完；两者都不允许静默换成 `trellis-*`。
3. 报告里要写出「哪个 kind 不可用、为什么、改走了哪条路」，不把这次降级说成正常派单。

### 3. 执行前确定分工（新增）

在「核心分工」下补一段可执行判据：

- 开始执行前先列出工作单元，每项标注「主会话 / 子 agent」；
- 交给子 agent 的判据：有明确输入、产物、验收方式，且能独立验证；
- 留主会话的判据：需要全局判断、跨模块契约、最终验收与集成，或改动小到派单成本更高（一行修复、配置值、回答问题）——这类要在交付说明里写出范围；
- 分工是决定的产物，不是按工具调用次数触发的提醒；不因此在对话里注入消息。

### 4. 与 Trellis inline 步骤的优先级（新增一句）

`.trellis/workflow.md` 的 Pi 分支写的是「自己实现、自己跑检查」。受管区说明：**执行归属以本文为准**；Trellis 的步骤描述的是「要做什么」，不改变「由谁做」。这是唯一一处需要点明冲突的地方，且不要求修改 Trellis 的生成资产。

## 落点

- `modules/agents/assets/main-AGENTS.region.md`：唯一改动点。
- `modules/agents/index.ts`：只在占位符集合变化时才改（`{{kindLimit}}` 等）；尽量不动，避免影响 `trellis update` 的整段覆盖语义。

## 风险

| 风险 | 处理 |
|---|---|
| 文本变长，模型抓不到重点 | 用表格与短句；三条规则各自一行，不写背景叙事 |
| 删掉 kind 名字后模型不知道派什么 | 保留「以 status 为准」+ 一次 `subagent({action:"list"})` 的读取方式 |
| 与 Trellis 文案继续打架 | 明确优先级的一句放在「核心分工」开头，不放在文末 |
